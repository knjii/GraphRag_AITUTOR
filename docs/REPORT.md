## 1. Кратко

Проект переписан в пакет `rag_textbook/`. Прежний каталог `src/` выведен
из эксплуатации. Написано **204 теста**, все проходят без GPU, Qdrant, Neo4j
и сервера инференса.

**Состояние на 2026-08-15: стек проверен вживую, качество измерено,
графовый компонент переработан по итогам измерений.** Ключевые числа —
в разделе 7.1. Коротко: индексация всей книги ускорилась с 14.5 ч до ~0.7 ч;
реранкер и расширенная квота выдачи дают значимый прирост; графовый канал
после трёх исправлений даёт значимый прирост recall +0.018 при шести
улучшенных вопросах и ни одном ухудшенном.

Три главных изменения по существу продукта:

1. **Формулы и таблицы перестали теряться.** Прежний чанкер заменял LaTeX формул
   и HTML таблиц на пересказ от модели зрения — в индекс попадала проза вместо
   самой формулы. Для ассистента по математической литературе это делало
   заявленную ключевую функцию неработоспособной.
2. **Граф перестроен, а не отключён.** Прежде 99.4% его рёбер были co-occurrence,
   построенные как «все пары топ-20 слов чанка». Теперь рёбра типизированы,
   сущности канонизированы лемматизацией, шум отсекается по PMI.
3. **Появился измеритель.** Retrieval-метрики считаются без LLM за секунды.
   До этого качество поиска оценивалось локальной моделью 4B на конце пайплайна,
   и разброс между прогонами превышал искомый эффект.

Полный перечень из 54 дефектов с решениями — [`MIGRATION-PLAN.md`](MIGRATION-PLAN.md).

## 3. Что было найдено

### 3.1. Окружение невоспроизводимо

Самая недооценённая проблема. `pip check` в рабочем окружении дал **30+ конфликтов**:

```
langchain-chroma 1.0.0      требует langchain-core>=1.0.0,  установлен 0.2.43
langchain-ollama 1.0.1      требует langchain-core>=1.0.0,  установлен 0.2.43
langchain-classic 1.0.0     требует langchain-core>=1.0.0,  установлен 0.2.43
langchain-huggingface 1.1.0 требует langchain-core>=1.1.0,  установлен 0.2.43
langgraph-prebuilt 1.0.5    требует langchain-core>=1.0.0,  установлен 0.2.43
langchain 0.2.17            требует numpy<2.0.0,            установлен 2.4.4
paddlepaddle-gpu 2.6.2      требует protobuf<=3.20.2,       установлен 7.34.1
magic-pdf 1.3.12            (MinerU 1.x) сосуществует с mineru 3.0.4
```

Это объясняло защитные `try/except` вокруг импортов в `rag_chain.py`,
`embeddings.py` и `llm.py`: код обходил сломанный граф зависимостей.

Отдельно: `paddlepaddle-gpu` против `protobuf 7.x` — paddle используется в OCR
внутри MinerU, и это кандидат в причины части нестабильности.

### 3.2. Чанкер уничтожал формулы

`src/chunker.py`, метод `_block_to_text`:

```python
if btype in self.special_types and use_description and block.get("llm_description"):
    text = block.get("llm_description", "")
    return self._apply_prefix(text, btype)   # возврат ТОЛЬКО описания
if btype == "equation": return block.get("text", "")   # сюда уже не доходим
```

При `special_types = {image, chart, table, equation}` и включённом обогащении:

| Тип блока | Что даёт MinerU | Что попадало в индекс |
|---|---|---|
| `equation` | LaTeX | одно предложение прозы |
| `table` | структурный HTML | markdown-пересказ от модели зрения |

Дополнительно это был самый дорогой этап индексации: модель зрения вызывалась
последовательно на каждый спец-объект, причём для таблиц и формул **дублировала
работу, уже сделанную MinerU**.

### 3.3. Граф работал как шумный BM25

Причины, по убыванию вклада:

1. **`CO_OCCURS` строились как клики.** Топ-20 «сущностей» чанка соединялись
   попарно — до 190 рёбер на чанк. Это не знание, а клика частотных терминов.
2. **70% корпуса обрабатывалось правиловым экстрактором** — узлы графа были
   сырыми токенами и биграммами, то есть мешком слов.
3. **Обход `RELATES|CO_OCCURS*1..2`** по графу с 280k co-occurrence-рёбер
   доставал практически весь граф.
4. **Ранжирование по `count(*)`** возвращало просто самые термин-плотные чанки.
5. **Seed-поиск не работал на русском**: точное совпадение сырых токенов почти
   всегда промахивалось, а fallback через `CONTAINS` делал полный скан по метке
   `Entity` и тащил случайные подстроки.

### 3.4. Прирост графа было нечем измерить

- В эталонном наборе **не было идентификаторов эталонных чанков** — только имя
  файла-источника. Recall@k посчитать невозможно в принципе.
- Поля `answer` и `contexts` предзаполнены прошлым прогоном системы — оценка
  частично сравнивала систему саму с собой.
- 30 вопросов дают доверительный интервал около ±18 п.п. при искомом эффекте
  в 5–10 п.п.
- Один документ-источник: межкнижные многошаговые связи не проверялись вовсе.
- Судья — та же локальная модель 4B. Разброс между прогонами: Contextual
  Precision 1.0 против 0.269, Faithfulness 1.0 против 0.357.
- В детальных результатах `contexts_count: 2` при `TOP_K=8` — метрики считались
  по двум контекстам из восьми.

### 3.5. Система не выдержала бы нескольких пользователей

| Проблема | Где было |
|---|---|
| Нет сервиса: процесс на вопрос | `query.py`, `app.py` |
| BM25 строился в RAM из всего корпуса при каждом создании цепочки | `retriever.py:660` |
| Chroma — файл SQLite; в коде уже был обработчик `disk I/O error` | `vectorstore.py:39` |
| Драйвер Neo4j создавался на каждый запрос, в двух ретриверах независимо | `retriever.py:305,456` |
| История чата: JSONL, полное чтение файла на ход, без изоляции пользователей | `chat_history.py` |
| Пароль Neo4j — обычное поле pydantic-ретривера, риск утечки в трейсы | `retriever.py:202` |

### 3.6. Прочее

- **Диалоговый RAG не работал**: `contextualize_q_system_prompt` объявлен, но
  history-aware retriever отсутствовал — поиск шёл по тексту последней реплики.
- **Метрика расстояния**: коллекция Chroma открывалась без указания косинуса,
  то есть работал L2 по ненормированным эмбеддингам.
- **Нет номеров страниц** у PDF-чанков: цитаты выводились как `p.?`.
- **`_env_bool("X", "0")`** возвращал `True` при пустом значении переменной.
- **`Settings`** — dataclass, значения читались один раз при импорте модуля.
- **Эмбеддинги считались 3–4 раза** для одного текста.
- **`.gitignore` исключал рабочий код**: `app.py`, `preflight.py`,
  `backfill_graph_from_chroma.py` не версионировались.
- **Тестов не было ни одного.** CI не было.

### 4.2. Исправление формул

`Block.to_indexable_text()` собирает текст так, чтобы **исходное представление
шло первым**, а описание от модели зрения — дополнением:

```
формула  →  $$A = U \Sigma V^{T}$$ Разложение матрицы на три множителя.
таблица  →  Таблица 1. Сингулярные числа | k | sigma | 1 | 5.2 | Пояснение...
```

Модель зрения вызывается только для `image` и `chart` — там, где своего
текстового представления действительно нет. Для таблиц и формул MinerU уже
отдаёт HTML и LaTeX, и повторная работа не нужна.

Результат обогащения кэшируется по хешу изображения и версии промпта, вызовы
идут параллельно.

### 4.3. Перестройка графа

| Было | Стало |
|---|---|
| `CO_OCCURS` как клики топ-20 слов | отсев по PMI и минимальной частоте; клики не строятся |
| обход `*1..2` по co-occurrence | 1 хоп по типизированным `RELATES`; многохоповый обход по `CO_OCCURS` **запрещён валидатором конфигурации** |
| ранжирование `count(*)` | взвешенная оценка с нормировкой на насыщенность пассажа терминами |
| сущности — сырые токены | канонизация лемматизацией; «сингулярных разложений» и «сингулярное разложение» — один узел |
| `CONTAINS` с полным сканом | full-text индекс Neo4j |
| свободный текст в метке связи | закрытый список из 9 меток |
| одна транзакция на 280k строк | батчирование |
| граф на каждый запрос | роутер по типу вопроса |
| нет кэша экстракции | кэш по `хеш чанка + модель + версия промпта` |

### 4.4. Измеритель

Retrieval-метрики (`Recall@k`, `Precision@k`, `nDCG@k`, `hit rate`, `MRR`)
считаются детерминированно, без LLM, за секунды. Есть разрез **по типам вопросов** —
именно он покажет, помогает ли граф там, где должен (multi_hop, relation),
а не «в среднем».

Эталонный набор строится **от чанка к вопросу**, поэтому идентификатор эталонного
фрагмента известен по построению. Многошаговые вопросы собираются из пар чанков,
связанных общими понятиями, но разнесённых по документу минимум на 10 чанков.

Функция `compare()` возвращает не только дельту, но и доверительный интервал
с предупреждением, если выборка мала.

### 4.5. Утилизация и защита от нехватки памяти

Два режима обхода корпуса:

- `document` — по документу целиком, экономно по оперативной памяти;
- `stage` (по умолчанию) — по стадиям: сначала разбираются все документы, потом
  все обогащаются и так далее.

Режим `stage` даёт два эффекта: в каждый момент на карте работает **один**
потребитель (нет конкуренции за память), и батчи становятся крупными
(эмбеддер получает тысячи чанков подряд).

Две страховки от нехватки видеопамяти:

- **упреждающая** — ожидание освобождения памяти по факту, а не по таймеру;
  размер батча подбирается по свободной памяти;
- **реактивная** — батч делится пополам и повторяется, нагрузка стадии
  снижается вдвое на весь оставшийся прогон; порядок обработки сохраняется.

Обе деградируют мягко: без `nvidia-smi` защита становится пустой операцией.

### 4.6. Мониторинг

Метрики пишутся **с привязкой к стадии конвейера**. Это принципиально:
«карта загружена на 45%» не позволяет принять решение, а «на разборе 92%,
на графе 12%» прямо указывает, что оптимизировать.

Классификация узкого места: `gpu` / `cpu` / `disk` / `waiting` / `mixed`.
Отдельно вычисляется `pipelining_likely_useful` — стоит ли перекрывать стадии.
Ответ утвердительный только когда тяжёлые стадии упираются в **разные** ресурсы:
на одной карте «GPU плюс GPU» не ускорится, стадии поделят её по времени.

### 4.7. Замена стека

| Компонент | Было | Стало | Почему |
|---|---|---|---|
| Векторное хранилище | Chroma (SQLite) | **Qdrant** | конкурентный доступ, явный косинус, детерминированные id |
| Лексический канал | BM25 в RAM | **sparse-векторы Qdrant** | русский стемминг, нет загрузки корпуса в память |
| Эмбеддинги | Ollama | **Infinity** (OpenAI-совместимый) | батчи, кэш, асимметричные префиксы |
| Реранкер | нет | **bge-reranker-v2-m3** | наибольший прирост качества на единицу усилий |
| Генерация | `ChatOllamaCompat` (300 строк поверх deprecated) | **OpenAI-совместимый `/v1`** | переход на vLLM — одна переменная |
| Конфигурация | dataclass | **pydantic-settings** | валидация, `SecretStr`, чтение при создании |
| Оркестрация | legacy-цепочки LangChain | **явный конвейер** | место под роутер и реранкер, видимый поток управления |

Оставлены без замены: **MinerU** (правильный инструмент, сменён только backend),
**Neo4j** (проблема была в дизайне графа), **Arize Phoenix**, layout-логика
собственного чанкера.

## 5. Что намеренно не перенесено

Три подсистемы в новый пакет не переехали. Решения обратимые, причины записаны.

### 5.1. KET-RAG

Отбор «ядра» по центральности с LLM-экстракцией только на нём.

Причины отказа:
- цель (сократить вызовы LLM) теперь достигается кэшем экстракции и
  параллелизмом; кэш экономит на **повторных** прогонах, которых при отладке
  большинство, а KET экономил только на первом;
- отбор стоил 2580 с на учебник, из них 43 минуты — повторное вычисление
  эмбеддингов, уже лежавших в хранилище;
- `_build_semantic_neighbors` строил плотную матрицу N×N: 50 МБ на 3533 чанках
  и около 40 ГБ на 100 тысячах — жёсткая стена по масштабу;
- правиловая экстракция на периферии давала узлы-токены, из которых и
  складывались клики co-occurrence, то есть KET ухудшал качество графа.

**Договорённость:** KET возвращается **после** снятия базовых метрик, как
измеряемый эксперимент по двум осям — экономия времени индексации и потеря
качества поиска. При возврате отбор ядра делать по числу типизированных связей
после первого прохода, без матрицы N×N и без повторного эмбеддинга.

### 5.2. Keyword-канал графа (`G_k`)

Узлы `:Keyword` содержали те же строки, что и `:Entity`, то есть дублировали
сущности; эмбеддинг усекался до 256 измерений и сравнивался косинусом на стороне
клиента. Лексический поиск теперь закрыт sparse-векторами Qdrant с русским
стеммингом, что делает канал избыточным.

### 5.3. Генеративные метрики DeepEval

Модуль `src/deepeval_eval.py` (1391 строка) остаётся в `src/` до переноса.
Новый харнесс закрывает метрики **поиска** — именно их не хватало для принятия
решений. Генеративные метрики требуют более сильного судьи, чем локальная 4B.

## 7.1. Измерено на сервере (2026-08-15)

Прогон на арендованном сервере с RTX 3090: вся книга, 512 страниц,
1151 фрагмент, эталонный набор из 172 вопросов.

### Стоимость индексации

| Стадия | Время | Узкое место |
|---|---|---|
| Разбор (MinerU, 5990 блоков) | 5.1 мин | ожидание, стадия однопоточна по разметке |
| Обогащение и чанкинг (225 иллюстраций) | 4.3 мин | карта, модель зрения |
| Векторизация (1151 фрагмент) | 0.2 мин | ожидание, стадия слишком коротка |
| Граф (1151 фрагмент, SGLang) | 71.7 мин | **карта, 99.6% загрузки** |

Итого около 1.4 часа против 14.5 часов у прежней версии. Разбор, чанкинг
и векторизация укладываются в 9.6 минуты; всё остальное — извлечение графа.

### Движки инференса

| Движок | Лучший параллелизм | Фрагментов в час | Масштабирование |
|---|---|---|---|
| Ollama (4-битное квантование) | 4 | 771 | 1.11× |
| SGLang v0.5.17 (bf16) | 4 | 1103 | 2.00× |

SGLang быстрее в 1.43 раза на нашей нагрузке, но при одном потоке медленнее:
Ollama держит модель в четырёхбитном квантовании. Выигрыш даёт именно батчинг.

Замечание из журнала движка: батч упирается **не** в KV-кэш (занят на 8%),
а в слоты состояния mamba — модель гибридная, а доля видеопамяти 0.55
отводит под них восемь слотов при двух запросах в очереди. Это неиспользованный
резерв, см. план.

### Качество поиска

| Метрика | Значение |
|---|---|
| recall@8 / recall@16 | 0.826 / 0.878 |
| nDCG@8 | 0.727 |
| MRR | 0.750 |
| hit rate@8 | 0.924 |

По типам вопросов recall@8: с формулами и таблицами 0.966, одношаговые 0.944,
**многошаговые 0.576**. Разрыв в 0.39 — главная слабость системы.

### Что даёт прирост, а что нет

Все сравнения парные, на одном наборе вопросов, с доверительным интервалом
по бутстрэпу.

| Изменение | Δ nDCG@8 | Δ MRR | Значимо | Вердикт |
|---|---|---|---|---|
| Реранкер | **+0.051** | **+0.088** | да | принято |
| Расширенная квота для связывающих вопросов | см. ниже | | | **принято** |
| Кандидатов реранкеру 30 → 60 | +0.000 | +0.001 | нет | отклонено |
| Схлопывание похожих фрагментов | +0.000 | +0.000 | нет | без эффекта |
| Разложение вопроса на подвопросы | −0.024 | −0.034 | да | **отклонено** |
| Графовый канал (включён/выключен) | +0.000 | +0.000 | нет | вклада нет |
| Графовый канал: старт от найденного | +0.000 | +0.000 | нет | вклада нет |

Расширенная квота измерена отдельно, потому что покупает качество за токены:

| Квота для связывающих | recall всего | recall многошаговых | Средний контекст |
|---|---|---|---|
| 8 (как у всех) | 0.826 | 0.576 | 8.0 фрагмента |
| **16** | **0.878** | **0.729** | 11.2 фрагмента |
| 20 | 0.890 | 0.763 | 12.8 фрагмента |

Задержка при этом не меняется (638 мс против 654 мс). Принято значение 16:
дальше отдача падает быстрее, чем растёт цена.

### Почему графовый канал сначала не давал прироста

Вывод получен измерением, а не рассуждением, и по дороге отброшены три
собственные гипотезы.

| Проверка | Результат | Что отброшено |
|---|---|---|
| Доля фрагментов графа вне векторной выдачи | 85.7% | «граф просто дублирует выдачу» |
| Качество стартовых сущностей | «сингулярный разложение svd», «матрица переход» | «сущности выродились в частотные хабы» |
| A/B с выключенным реранкером | 12 лучше / 25 хуже | «реранкер стирает вклад графа» |
| Вес графа 0.4 → 0.8 | recall −0.075, значимо | «граф недовешен» |
| Обход на два шага вместо одного | изменение на 1 вопросе | «не хватает глубины обхода» |

Найдены три причины, каждая устранена.

**Причина 1: связи извлекались внутри одного фрагмента.** Экстрактор видел
текст одного чанка, поэтому любое ребро `RELATES` соединяло сущности,
встретившиеся в одном и том же тексте. Обход такого графа приводит
к фрагментам, разделяющим слова с запросом, — то есть делает работу
лексического поиска, только хуже. Граф физически не мог содержать сведений,
которых нет в отдельных фрагментах.

Решение — извлечение связей из сопоставления выдержек об одном понятии
из разных мест книги (`GRAPH_CROSS_CHUNK_ENABLED`). На 250 понятиях получено
942 связи, из них 140 не выводимы из отдельного фрагмента. Доля типизированных
рёбер выросла с 67.9% до 72.0%. Стоимость — 103 секунды.

**Причина 2: измеритель не мог показать пользу графа.** Многошаговые вопросы
набора строились из пар фрагментов с не менее чем тремя общими терминами,
то есть **лексически связанных** — ровно там, где векторный и лексический
каналы справляются сами.

Решение — отбор пар, соединённых типизированной связью графа, но почти
не пересекающихся по словам (тип вопроса `graph_linked`). Разница видна сразу:

| Набор | вектор@30 | граф@30 | граф находит то, чего нет у вектора |
|---|---|---|---|
| лексически связанные пары | 0.939 | 0.628 | 0.006 |
| **связанные графом пары** | 0.775 | 0.739 | **0.101** |

**Причина 3: вклад терялся до реранкера.** Найденный графом материал не
доходил до контекста: ранговое слияние ставило его ниже плотной векторной
выдачи, а до реранкера доезжали только первые 30 кандидатов. Показатель
`graph_only_share` равнялся нулю при 18% присутствия графа в контексте.

Решение — резерв мест в пуле кандидатов за фрагментами, которые нашёл
**только** граф (`RETRIEVAL_GRAPH_CANDIDATE_QUOTA`). Резерв ничего не
навязывает ответу: он доводит фрагменты до реранкера, решает по-прежнему
реранкер.

### Результат: граф даёт значимый прирост

Итоговое сравнение, 163 вопроса, парный бутстрэп, k=16:

| Метрика | без графа | с графом | Δ | 95% интервал | лучше/хуже | Значимо |
|---|---|---|---|---|---|---|
| recall | 0.841 | **0.859** | **+0.018** | [+0.006; +0.034] | **6 / 0** | да |
| precision | 0.109 | 0.112 | +0.002 | [+0.001; +0.004] | 6 / 0 | да |
| nDCG | 0.746 | **0.752** | **+0.006** | [+0.002; +0.011] | **12 / 0** | да |
| MRR | 0.789 | 0.790 | +0.000 | [−0.000; +0.001] | 2 / 1 | нет |

На вопросах, ради которых граф и строится, прирост крупнее: recall
`graph_linked` 0.710 → **0.754**. Ни один вопрос не ухудшился.

Показатель вклада: `graph_only_share` 0.000 → **0.023**. Задержка не выросла
(673 мс против 670 мс).

Прирост скромный, и это стоит сказать прямо: 6 вопросов из 163 по recall.
Но он положителен, значим, никого не ухудшает и получен на измерителе,
который специально построен так, чтобы не льстить графу.

### Итоговое качество

| k | recall | nDCG | hit rate |
|---|---|---|---|
| 8 | 0.819 | 0.738 | 0.945 |
| 12 | 0.840 | 0.746 | 0.957 |
| 16 | **0.859** | **0.752** | **0.963** |

MRR 0.790. По типам recall: с формулами 0.958, одношаговые 0.913,
связанные графом 0.754.

### Принятая конфигурация

| Параметр | Значение | Основание |
|---|---|---|
| `RETRIEVAL_TOP_K_LINKING` | 16 | recall многошаговых 0.576 → 0.729 |
| `RETRIEVAL_GRAPH_CANDIDATE_QUOTA` | 6 | вклад графа 0.000 → 0.023 |
| `GRAPH_SEED_MODE` | `both` | лучший из трёх режимов на замере |
| `GRAPH_CROSS_CHUNK_ENABLED` | `1` | +140 рёбер между фрагментами |
| `GRAPH_CROSS_CHUNK_MAX_ENTITIES` | 250 | 1200 понятий дают вдвое больше рёбер и прирост **меньше** |
| `SGLANG_GPU_FRACTION` | 0.75 | пропускная способность 1103 → 2094 фрагмента в час |
| `LLM_MAX_CONCURRENCY` | 16 | лучшая точка по замеру `bench` |
| `RETRIEVAL_DECOMPOSE_ENABLED` | `0` | проверено, значимо хуже |

## 8. Чего проверка не доказывает

Здесь важно не переоценить сделанное.

1. **Эталонный набор не вычитан человеком.** 172 вопроса сгенерированы моделью
   по фрагментам корпуса. Для сравнения конфигураций между собой этого хватает —
   обе стороны видят одни и те же вопросы. Для заявлений об абсолютном качестве
   продукта не хватает: набор надо просмотреть и проставить `verified: true`.
2. **Набор не может показать пользу графа.** Многошаговые вопросы построены
   из лексически пересекающихся пар фрагментов (не менее трёх общих терминов).
   Это ограничение измерителя, разобранное в 7.1.
3. **Качество ответа не измерено, измерено качество поиска.** Retrieval-метрики
   говорят, дошёл ли нужный фрагмент до контекста. Насколько хорош текст ответа —
   отдельный вопрос, генеративные метрики остаются в прежнем `src/deepeval_eval.py`.
4. **Замеры на одном учебнике.** 1151 фрагмент, одна предметная область,
   один язык. Перенос на другой корпус требует повторного замера.
5. **Разбор PDF не сверялся с эталоном.** OmniDocBench не прогонялся, поэтому
   утверждать точность распознавания формул и таблиц нельзя — известно лишь,
   что LaTeX доходит до индекса и что 763 фрагмента из 1151 содержат формулы.
6. **Один прогон на конфигурацию.** Retrieval-метрики детерминированы, поэтому
   разброс между прогонами нулевой, но случайность сборки набора не усреднялась.

## 9. План: что делать дальше и почему именно это

### 9.1. Графовый компонент

Три причины бесполезности графа устранены (раздел 7.1), граф даёт значимый

понятий до 1200. Рёбер стало 5162 вместо 4251, доля типизированных выросла
до 76.4%, а прирост **снизился** — recall +0.015 против +0.018, пять
улучшенных вопросов вместо шести. Разница в пределах шума, но улучшения нет:
лишние рёбра вносят столько же шума, сколько сигнала. Значение 250 оставлено
как измеренный оптимум.

Что осталось:
